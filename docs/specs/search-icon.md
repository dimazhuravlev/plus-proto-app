## 4. Причина сдвига −4pt (не в самой иконке, а в раскладке SearchPill)

`ActionBarView.swift`, `SearchPill.body`:
```swift
HStack(spacing: 8) { searchIcon; ZStack{…}; if isSearchFocused { clearButton } }
    .padding(.horizontal, ActionBarGeometry.searchPaddingH)   // 18
    .frame(width: layout.searchWidth)                         // 60 в .music
```
Контентная область = 60 − 18 − 18 = **24pt**. Дети HStack: `searchIcon` фиксированные 24 + spacing 8 + гибкий ZStack, который схлопывается в 0. Итого требуется 32 > 24 → HStack переполняется на 8 и центрируется → **всё содержимое уезжает на −4pt**. Бокс иконки встаёт в x 14…38 вместо 18…42. Зазор 8pt не исчезает вместе со схлопнувшимся полем ввода. Совпадение аналитики (15.743) и замера (15.667) — 0.076pt, т.е. в пределах 1/4 пикселя.

## 5. Что менять

**A. Ассет (исправляет форму глифа и остаточные 0.26pt).**
Заменить `PlusProtoApp/Assets.xcassets/iconSearch.imageset/iconSearch.svg` содержимым `/tmp/search-icon/iconSearch-figma-24.svg`. Ключевое: брать вариант **24×24 с путём на своём месте (2,2)**, а не tight-crop. Тогда `glyphSize(of:"iconSearch", box:24)` (ActionBarView.swift:608) вернёт natural 24×24, fit = 1, и глиф ляжет ровно в фигмовские (20,20)…(39.5605,39.5605), включая оптическое смещение 0.21973pt вверх-влево, которое иначе теряется при центрировании. Код `searchIcon` при этом менять не нужно вообще. `Contents.json` не трогать — `preserves-vector-representation: true` и `template-rendering-intent: template` уже верные.

**B. Раскладка (исправляет −4pt).** В `SearchPill.body` убрать общий spacing и повесить зазор на иконку, чтобы он схлопывался вместе с полем:
```swift
HStack(spacing: 0) {
    searchIcon
        // Зазор схлопывается вместе с полем: иначе 24+8 не влезает
        // в 24pt между полями 18 и HStack сдвигает лупу на 4pt влево.
        .padding(.trailing, layout.searchIconOnly ? 0 : 8)

    ZStack(alignment: .leading) { … }

    if isSearchFocused {
        clearButton.padding(.leading, 8)   // spacing 8 был общим — вернуть явно
    }
}
```
`padding` анимируется, так что морф остаётся плавным. Бонус: после правки бокс иконки стоит на x=18 в ОБОИХ состояниях, значит при морфе music↔search лупа вообще не двигается (сейчас она проскакивает 4pt).

Более дешёвая альтернатива, если не хочется трогать структуру: оставить `HStack(spacing: 8)` и добавить на `searchIcon` `.offset(x: layout.searchIconOnly ? 4 : 0)` — чистый трансформ без релэйаута, но с магической константой, завязанной на spacing.

## РИСКИ
- Если взять tight-crop вариант (19.5605) вместо 24×24, glyphSize отцентрует глиф в боксе и потеряется фигмовское оптическое смещение 0.21973pt вверх-влево. Для пиксель-в-пиксель нужен именно 24×24.
- Правка B меняет общий spacing HStack с 8 на 0 — обязательно вернуть 8pt зазор перед clearButton явным .padding(.leading, 8), иначе крест прилипнет к полю ввода в состоянии фокуса.
- clearButton использует тот же glyphSize с ассетом iconClose. Если iconClose тоже обрезан впритык (а не 24×24 с фигмовскими полями), у него та же проблема неточного позиционирования — стоит проверить отдельно, в эту задачу не входило.
- После правки B бокс иконки встаёт на x=18 в обоих состояниях, поэтому при морфе music↔search лупа перестанет проскакивать 4pt. Это изменение анимации — нужно посмотреть глазами, что морф выглядит как задумано.
- padding в правке B анимируемый и вызывает релэйаут HStack на кадр морфа, но это тот же класс стоимости, что уже есть у анимации ширин зон. GeometryReader не используется — ограничение проекта соблюдено.
- Замер по скриншоту сделан порогом 50% покрытия, гранулярность 1/3pt (×3). Расхождение аналитики (15.743) и замера (15.667) 0.076pt — в пределах погрешности, на вывод не влияет.
- PNG-рендер ноды из Figma подтверждённо непрозрачный (alpha 255, фон #444 запечён) — растр из Figma для этой иконки использовать нельзя, только SVG.
