## 3. Вывод: что и на сколько рассинхронизировано

**Дефект №1 — правая зона не анимируется вообще (это и есть жалоба пользователя).**
Обложка мини-плеера стоит на месте: `coverTop` = 720.83pt на кадрах 172→182 (дрейф 0.0–2.0pt = шум), `coverCx` = 121.8 → 123.8pt (≤2pt). За это же окно поиск поднялся на 13.3pt, а всего поднимается на 242.3pt. Расхождение по вертикали:
- кадр 178 (первый кадр движения): **13.3pt**
- кадр 180: **13.0pt**
- кадр 182: **47.1pt** (поиск 691.9, плеер эквивалентно 739)
- дальше плеер уже полностью под клавиатурой и просто гаснет там же, где стоял.

Горизонтально: **0 из 128pt** (8pt схлопывания зазора + 120pt `trailingEscape`). Полоса у правой кромки не загорается ни разу.

**Дефект №2 — подъём отстаёт от клавиатуры примерно на 50 мс и идёт по своей кривой, из-за чего весь бар ныряет под клавиатуру.**
Клавиатура тронулась ~t=3.51 (на кадре 173, t=3.527, она уже прошла 5.5 %), бар тронулся между t=3.557 и t=3.567 → **лаг ≈ 50 мс**. В момент, когда клавиатура прошла 51 % пути, бар прошёл 5.4 %. `barBot − kbTop` положительна с кадра 177 (t=3.557) по кадр 199 (t=3.720) — **170 мс бар частично под клавиатурой**, максимум перекрытия **54.6pt из 60pt высоты бара** (кадр 182): на экране остаётся полоска 5.4pt. На кадрах 180–186 бар визуально исчезает целиком и потом «всплывает» из-под клавиатуры.

**Дефект №3 (второстепенный) — три кривые вместо одной.** Поля бара 24→16 идут по 0.25 (норм. прогресс совпадает с подъёмом: 26 %/44 %/51 %/64 %/71 %/79 % на кадрах 182/185/187/190/192/194), а ширины зон и opacity — по 0.32. Даже если починить №1, левая и правая половины будут доезжать в разные моменты.

## 4. Какие именно модификаторы это вызывают

1. **`ActionBarView.swift:421-423` — `.if(layout.clipTrailing) { view in view.clipped() }`.** Главная причина. `@ViewBuilder if/else` даёт `_ConditionalContent`; `clipTrailing` переключается `true → false` (`:186` → `:158`), значит вся `TrailingSlot` меняет идентичность вью. SwiftUI удаляет старое поддерево (дефолтный `.opacity`-переход под анимацией A, 0.32 с) — удалённое поддерево **больше не участвует в раскладке и рисуется замороженным в последней геометрии**, — и вставляет новое, которое рождается сразу с `offset(x: 120)` (`:419`), `opacity 0` (`:420`) и шириной 0 (`:415`), то есть невидимым. Поэтому `offset(x:)` и `offset(y:)` физически не к чему применить.
   Режимы, где ветка переключается: `.search` (`:172`), `.music` (`:186`), `.movie` (`:229`) — дефект есть. `.book` (`:216`) — ветка не меняется, дефекта нет (подтверждено контролем).
2. **`BottomChrome.swift:99` — `.animation(.smooth(duration: 0.25), value: focusedOffset)`** вместе с **`:112-118 focusedOffset`** (условие `keyboard.overlap > 0` + `isSearchFocused`, который ставится через `onChange(of: searchFocused)` в `ActionBarView:84-86`, то есть на такт позже нотификации клавиатуры). Это даёт стартовый лаг ~50 мс.
3. **`BottomChrome.swift:172` — `withAnimation(.smooth(duration: duration))`** вокруг `overlap`. `.animation(_:value:)` из п.2 заменяет транзакцию, поэтому системная кривая клавиатуры отбрасывается: `overlap` меняется ступенькой, а бар едет собственной `.smooth(0.25)`, никак не связанной с реальной кривой клавиатуры.
4. **`ActionBarView.swift:81-83` — `.padding(.horizontal, …)`** стоит выше `.animation(morph, …)` из `:77`, поэтому управляется не 0.32, а 0.25 из `BottomChrome:99`. Побочно: `.animation(_:value:)` выставляет анимацию поддерева в `nil`, когда `value` не изменился — если `isSearchFocused` и `focusedOffset` разойдутся по разным апдейтам, поля 24→16 щёлкнут мгновенно (в этой записи они совпали, поля анимировались плавно).
5. **`BottomChrome.swift:104` — `.animation(morph, value: isSearchFocused)`** для бара мёртвый: перекрыт внутренним `:99`.
