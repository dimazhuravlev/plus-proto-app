# Как мы работаем вдвоём

Проект ведут два дизайнера, а не команда разработки. Поэтому правила ниже — про то,
чтобы не мешать друг другу и не ломать `main`, а не про код-ревью и процессы.

Главное в одну строку: **ветка → pull request → зелёная сборка → Squash and merge**.
В `main` напрямую не пушим — на нём собранное состояние, от которого оба стартуют.

## Цикл работы

```bash
# 1. Забрать свежий main
git checkout main && git pull

# 2. Своя ветка под задачу
git checkout -b feat/album-track-player

# 3. Работать. Перед коммитом — собрать у себя
xcodebuild -project PlusProtoApp.xcodeproj -scheme PlusProtoApp \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -configuration Debug build

# 4. Коммит и пуш
git add -A && git commit
git push -u origin feat/album-track-player

# 5. Pull request
gh pr create --fill --base main
```

Дальше на GitHub: дождаться зелёной галочки проверки «Сборка», нажать **Squash and merge**
и **Delete branch**. Второй участник забирает результат через `git checkout main && git pull`.

Если кнопки `gh` нет под рукой — всё то же самое делается на сайте, PR предлагается
сам сразу после пуша ветки.

### Имена веток

`feat/` — новое, `fix/` — починка, `docs/` — только документация. Дальше короткое
описание латиницей через дефис: `feat/search-empty-state`, `fix/album-cover-clip`.

### Коммиты

По-русски, Conventional Commits, как в истории: строка-заголовок «что стало», а в теле —
**почему** так, а не перечень изменённых файлов. Тело важнее заголовка: через месяц
ответ на «почему» не восстановить ниоткуда, кроме него.

## Ревью: что проверяет робот, что человек

**Робот** (GitHub Actions, `.github/workflows/build.yml`) на каждый PR собирает проект
на Xcode 26.3. Красная проверка означает ровно одно: ветка не компилируется, мержить
нечего. Ничего про вёрстку и анимации она не знает.

**Человек** — только автор ветки, глазами в симуляторе. Апрув второго не требуется и
не настроен: мы оба дизайнеры, построчное чтение чужого Swift никому не поможет, а ждать
его — терять день. Зовите друг друга на посмотреть, когда правка спорная: не апрувом,
а просто «глянь, так лучше?».

Правило простое: **мержит тот, кто сделал**, как только сборка зелёная и он сам
посмотрел результат в симуляторе.

## Чтобы ветки не конфликтовали

1. **Короткие ветки.** День-два работы, не неделя. Чем дольше ветка живёт, тем больше
   в ней расходится с `main`.
2. **Делим зоны.** Договаривайтесь заранее, кто в каких экранах: два человека в одном
   `ActionBarView.swift` за один день — это гарантированный конфликт.
3. **Обновляем ветку перед мержем**, если `main` уехал вперёд:
   ```bash
   git checkout main && git pull
   git checkout feat/моя-ветка && git merge main
   ```
   Конфликт разрешается здесь, у себя, где можно тут же пересобрать. На GitHub
   разрешать конфликты не надо.
4. **`docs/DECISIONS.md` склеивается сам.** Оба пишут туда новые записи сверху —
   для этого файла включён `merge=union` (см. `.gitattributes`): при локальном мерже
   обе записи остаются, конфликта нет. Проверять глазами всё равно стоит: union
   не понимает смысла, он просто сохраняет обе стороны.
5. **`.xcodeproj` трогать почти никогда не нужно** — папка `PlusProtoApp`
   синхронизирована с файловой системой, новые файлы просто кладутся на диск.
   Это и убирает главный источник конфликтов в iOS-проектах.

## Что не коммитим

- `PlusProtoApp/APIKeys.swift` — ключи. В гитигноре, и пусть там и остаётся.
- `_secrets/`, `DerivedData/`, `xcuserdata/`, `.DS_Store` — тоже в гитигноре.
- Скриншоты прогонов и временные файлы: складывать в `/tmp`, а не в репозиторий.

## Правила самого проекта

Они не про git и лежат отдельно:

- [CLAUDE.md](CLAUDE.md) — конвенции: токены, отладочные флаги, верификация руками.
- [docs/HANDOFF.md](docs/HANDOFF.md) — состояние дел, приёмы проверки, полный список флагов.
- [docs/DECISIONS.md](docs/DECISIONS.md) — лог решений. **Каждое решение пишется туда
  в тот же день**, вместе с причиной. Это главный договор проекта: без «почему» через
  неделю любое решение выглядит случайным и переделывается по кругу.
